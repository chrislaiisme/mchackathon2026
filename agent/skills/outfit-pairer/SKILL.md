# outfit-pairer

從已經生好的六件上衣與六件下身裡，挑出**一組**最搭的，並用**一句**繁體中文講出為什麼。

只做配對。不生圖、不檢索商品、不排序商品、不問使用者問題、不改意圖、不回傳第二組備案。
衣服長什麼樣在這支 skill 跑之前就已經定了——這裡只讀它們的屬性，不產生新的衣服。

## 輸入

- `intent`：ENGINE01 的結構化意圖（第 2 輪起是 ENGINE03 的 `updated_intent`，型別相同）。
  它是**整體脈絡**，不是候選之一：場合、季節、風格關鍵字、顏色都在這裡。
  `inferred_fields` 列到的欄位是系統替使用者補的，不是他親口講的——這個差別會影響讓步順序。
- `tops`、`bottoms`：各一份清單，每筆是 `{ id, label, keywords }`。
  - `id`：`top-ai-3`／`bottom-ai-6` 這種形狀，**輸出只能從這兩份清單裡挑**。
  - `label`：這件跟其他幾件的差別（`varied_label`），例如「及膝」「落肩箱型」。
  - `keywords`：欄位 → 中文值，由 `concept-image-director` 寫進 manifest 的那一份
    （`item_type`、`fit`、`length`、`silhouette`、`material`、`colors`、`pattern`、
    `design_detail`、`detail_placement`…）。判斷靠這一份，不要只看 `label`——
    `label` 只講了六格之間變動的那一個軸，其餘屬性都在 `keywords` 裡。

上衣與下身各自內部已經是可比較的（同一張六宮格、同一套打光），所以這裡不做圖像層的判斷。

## 步驟

1. 讀 `intent`，分出**鎖死條件**（使用者親口講的）與**可讓步的**（`inferred_fields` 裡的）。
2. 先刷掉硬衝突：場合不合、季節不合、材質重量差一個級距以上的組合，直接不考慮。
3. 對活下來的組合看輪廓平衡與長度關係，挑出最好的一組。
4. 寫一句理由，句子裡要指名兩件各自的具體屬性。
5. 輸出一組 id ＋ 那句理由。

## 判斷依據

<!-- prompt:rules:start -->
下面四條依序看，前面的條件不滿足就不必看後面的。

**一、輪廓平衡——一鬆一合。**
落肩箱型、oversize、寬鬆的上衣，配直筒或錐形的下身；上衣本來就寬，下身再配寬鬆桶褲或
闊腿，整個人會變成一個方塊，腰線消失。反過來合身短版上衣可以配寬鬆桶褲、闊腿或喇叭，
上窄下寬是成立的。兩件都貼身只有在 `intent` 明講了 cleanfit、韓系、層次這類字眼時才選，
否則它是「沒搭過」而不是「搭得好」。

**二、長度關係——上衣下擺落在哪、腰線在哪。**
短版上衣要配高腰，中間不要留一截空白；長版或蓋過臀部的上衣配高腰闊褲會把腿整個吃掉，
那時下身要收窄，或選露得出腳踝的長度。下身如果是及膝、九分這類會在小腿製造切點的長度，
上衣的下擺就不要停在同一個高度——兩條橫線疊在一起，身型會被切成三段。

**三、材質與場合要在同一個調子上。**
重量級距要接近：厚磅刷毛、粗織不配雪紡、薄針織；丹寧配丹寧要確認水洗色不同，
否則會變成一整套牛仔套裝。工裝尼龍配西裝毛料是材質衝突，只有 `intent` 講過要衝突、
要街頭、要混搭時才是加分。場合與季節一起看：通勤、正式場合不要放刷破與大面積漂白；
夏天不要配厚磅。

**四、要貼合 `intent` 講過的東西。**
使用者親口講的顏色、風格關鍵字、場合、材質，在選中的這一組上要看得見；
`inferred_fields` 裡的值是我們替他補的，跟前三條打架時先讓它。
`design_detail` 兩件都很強（兩邊都有單側褲鏈、大面積漂白這種主角級細節）時，
只留一件當主角，另一件要素——兩個主角互相搶戲，使用者說不出他喜歡的是哪一個，
ENGINE03 也聚合不了。

**理由怎麼寫。** 一句繁體中文，40 字以內，要同時指名上衣與下身各自的具體屬性，
以及它們之間的關係（收窄、放寬、腰線、長度、水洗色、材質重量）。
「這樣很好看」「很百搭」「風格一致」不算理由——那種句子換成任何一組都成立。
不要點名品牌或設計師，不要用「我」「使用者」，直接講搭配本身。

## 輸出

```json
{
  "top_id": "top-ai-3",
  "bottom_id": "bottom-ai-6",
  "reason": "落肩箱型上衣配錐形丹寧褲，肩線放寬、褲管收窄，腰線沒有被吃掉。",
  "source": "llm"
}
```

- `top_id`、`bottom_id`：**必須逐字出自輸入的清單**。自己拼一個 `top-ai-7` 出來，
  前端在 `FashionRecommendation` 裡找不到這個 id，那一組就顯示不出來。
- `reason`：一句繁體中文，指名具體屬性（見上面「理由怎麼寫」）。
- `source`：`llm` 是模型真的挑的；`fallback` 是模型失敗或回傳不合法時，
  由腳本退到 `tops[0]` 與 `bottoms[0]` 並用 `keywords` 拼出來的。
  前端要分得出來——`fallback` 的那句話是拼的，不是判斷出來的。

## 不要做的事

- 不要挑清單以外的 id，也不要回傳第二組備案。要挑的就是一組。
- 不要只看 `label` 就決定。`label` 只有一個軸，其餘屬性在 `keywords` 裡。
- 不要因為「六件都不夠好」就不挑。清單有東西就一定要出一組——
  這條線的退場是`fallback`，不是空手而回。
- 不要改意圖、不要補問題、不要順手推薦第三件（外套、鞋、包）。
- 不要生圖，也不要為了配得更好而要求重生單品。
- 不要點名真實品牌或設計師。
