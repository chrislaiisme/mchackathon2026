## 1. 介面規格（要和 ENGINE 01／03 負責人確認）

完整定義見 `engine02/contracts.py`（Pydantic），版本 `0.1.0`。

### 1.1 輸入 `Engine02Request`

| 欄位 | 來源 | 說明 |
|---|---|---|
| `constraints.{category,color,occasion,season,gender,style_keywords}` | ENGINE 01 M1 | 每欄 `state` ∈ `unmentioned / value / dont_care / inferred`（PRD 四態）。**`value` 才當硬過濾**，`inferred` 只當軟訊號。值必須是商品庫詞彙（見 §4.1）。 |
| `constraints.budget` | ENGINE 01 M1 | `max_price / min_price`；目前商品庫沒有價格，會自動放寬並標示 |
| `constraints.excluded_values` | ENGINE 03 `exclude(屬性,值)` | 永遠不放寬 |
| `needs[] = {need_id, prob}` | ENGINE 01 M2 | p(n)，`need_id` 必須存在於感性對照表 |
| `retrieval_text`（**新增提議**） | ENGINE 01 | 一句**英文、不含否定詞**的短描述。原因：商品庫是英文、使用者講中文；CLIP 類模型對否定詞接近隨機（CVPR 2025 NegBench，本機實測差距 ≤0.03） |
| `feedback.design_adjust_steps` | ENGINE 03 `adjust(d,±1)` | 每步 0.25，上限 ±3 步，由 ENGINE 02 換算成 Δβ |
| `feedback.chosen_item_ids / rejected_item_ids` | ENGINE 03 choice | Rocchio 正例／負例，加上「和否決商品相似」的懲罰項 |
| `feedback.excluded_item_ids` | ENGINE 03 | 不再出現 |
| `feedback.anchor_item_ids` | ENGINE 01／03 | 使用者要拿來一起穿的商品；**有值才會計算穿搭相容性** |
| `feedback.concept_image_embedding`（提議） | 生成分支 | 預設權重 0（對照組 0.2），理由見 §3.6 |

### 1.2 輸出 `Engine02Response`

每張卡片 `RankedItem`：
- `score` = Σ `contributions[].contribution`（**加總完全等於總分**，測試強制檢查）
- `contributions[]`：每一項的 `raw / normalized / weight / contribution`，設計要素項另外附 `need_shares`（哪個需求貢獻多少，加總等於該項貢獻）
- 三種理由判定一次全給：`rank_without / necessary`（PRD 反事實）、`diff_vs_cutoff`（和第 k+1 名的對比）、`sufficient`（最小充分集合），`cited` 標出**卡片上實際顯示的**那幾項
- `design_scores`：這件商品所有 c(i,d)，**ENGINE 03 算 S(i|n)=Σ_d K[n,d]·c(i,d) 直接用**
- `reasons`（模板句，每條都對應一個 cited 項）、`explanation`、`explanation_source`（llm／template）

整輪的回傳：
- `constraint_report`：套用了哪些條件、依序放寬了哪些
- `metrics`：規則計算的硬條件滿足率、被排除值出現次數、違反回饋次數（PRD §7，**不是用排序分數算的**）
- `query_embedding`：本輪查詢向量，提供給 ENGINE 03 或下一輪做 Rocchio

## 2. 架構

```
Engine02Request
  │
  ├─ 1. 硬條件過濾（pandas mask）→ 結果不足 k 件時依序放寬：
  │     顏色允許缺值 → 季節允許缺值 → 場合允許缺值 → 拿掉季節 → 拿掉場合 → 預算×1.2 → 拿掉顏色 → 拿掉預算
  │     （品類、性別、排除值永遠不放寬；只記錄真的讓結果變多的步驟）
  │
  ├─ 2. 候選召回（過濾後的商品池內精確計算）
  │     dense：Marqo-FashionSigLIP 圖片向量 · 查詢向量（有回饋時做 Rocchio）
  │     sparse：BM25（rank_bm25）over title＋subcategory＋color
  │     融合：RRF(k=60) / 正規化 convex / 依查詢詞命中率調整的 RRF → top-50
  │
  ├─ 3. 可加總 reranker（用商品池統計量標準化）
  │     S(i) = w_dense·z(dense) + w_bm25·z(bm25)
  │          + Σ_d β_d · c(i,d)          β_d = Σ_n p(n)K[n,d] + 0.25·steps_d
  │          + w_compat·compat(商品, 錨點)       ← 只在有錨點時；OutfitTransformer，無模型時退回品類 NPMI
  │          + w_trend·z(趨勢 BM25) − w_pen·z(和否決商品的最大相似度)
  │          [+ w_rerank·z(cross-encoder)]       ← GPU 才開
  │     [MMR 多樣化（對照組）]
  │
  ├─ 4. 理由判定：必要性（PRD）／對比邊際／最小充分集合（預設）
  └─ 5. 模板理由 →（有 key 時）LLM 改寫 → 數字與標籤事實檢查 → 失敗就用模板
```

商品資料：`Marqo/KAGL`（公開、卡片標 MIT、有顏色／季節／場合／性別，**沒有價格**）目前 5,000 件；穿搭共現統計來自 `Marqo/polyvore` 的 21,587 組穿搭。細節見 `docs/research/catalog-options.md`。

## 3. 實驗

### 3.0 設定與限制（先讀）
- 商品庫是 KAGL 的 5,000 件（shuffle buffer 抽樣，不是真正的隨機樣本）；筆電 CPU。
- **不用 LLM，也沒有人工標註**：標準答案全部來自資料集屬性，image encoder 看不到這些屬性。所以這些都是**代理指標**，簡報上要照實說明。
  §3.3 的 420 筆目視標註是**LLM 標註者**做的，所以那些 AUROC 是模型對模型。要把這個缺口補起來：`data/labels/human_tasks.csv`（已產生 140 題盲標，依設計要素分層、不含 LLM 標籤）給真人填 `label` 欄（1／0／na），再跑 `python scripts/eval_human_agreement.py score --human <檔案> --encoder marqo-fashionSigLIP`，就會印出每個要素的 Cohen's κ、雙方的「無法判斷」比例，以及同一批商品在**人工標準答案**與 LLM 標準答案下的 AUROC 對照。若人工那欄明顯較低，代表標註者與打分模型有共同盲點，§3.3 的數字偏樂觀，簡報必須講明。
- 60 句查詢、100 個模擬目標；統計用 query 層級配對置換檢定（10,000 次）與 bootstrap 95% 信賴區間。
- 原始檔在 `reports/ablation/kagl_<encoder>/`，指令：`python scripts/run_ablation.py --encoder <name>`。

### 3.1 T1 檢索品質（NDCG@5；等級：子類＋顏色＋性別＋場合全對 3，子類＋顏色 2，子類 1）

| 設定 | fashion-clip 用詞相同 | fashion-clip 換句話說 | Marqo 用詞相同 | Marqo 換句話說 |
|---|---|---|---|---|
| BM25 | 0.758 | 0.034 | 0.758 | 0.034 |
| dense | 0.569 | **0.426** | 0.614 | **0.463** |
| hybrid RRF | 0.821 | 0.193 | 0.830 | 0.191 |
| hybrid convex | **0.868** | 0.110 | **0.865** | 0.119 |
| full（可加總，無需求） | 0.842 | 0.093 | 0.840 | 0.093 |
| RRF＋依命中率調整 BM25 | 0.821 | 0.195 | 0.830 | 0.206 |
| full＋依命中率調整 BM25 | 0.842 | 0.169 | 0.840 | 0.175 |

換句話說的查詢把子類、顏色、性別、場合都換成同義詞（tee、midnight、guy's、workout），用來模擬 ENGINE 01 **沒有**做詞彙正規化的情況。

解讀：
- 用詞和商品庫一致時，混合檢索比純 dense 高 0.22–0.30（p<0.001）。
- 用詞不一致時，BM25 只會帶進雜訊，連依命中率調整權重都救不回來。
- **所以詞彙正規化是 ENGINE 01 的硬性需求**，不是加分項。
- **「用詞相同」是上界情境，不要當成真實表現**：這欄的查詢字面上就取自商品屬性，所以字面重疊被灌水——同型態查詢下光 BM25 在外部語料就有 R@1 0.859（KAGL）、0.992（H&M）、MRR@10 甚至到 1.000（DeepFashion）。在**唯一有真人標註**的真實查詢資料（Amazon ESCI）上，加 BM25 相對純 dense 的邊際貢獻只有 **+0.003 nDCG@10**（小但穩定，§3.20）。混合檢索的價值在於硬條件詞彙命中，不是在於這個 0.22–0.30 的差距。
- Marqo 和 fashion-clip 在這份 5,000 件的資料上差距不顯著，44k 全庫跑完再下定論。

每次查詢延遲（筆電 CPU，不含 LLM）：fashion-clip 約 60 ms，Marqo 約 95 ms。

### 3.2 T2 硬條件（同時指定品類、顏色、性別、場合 4 個條件）
- 23% 的查詢需要放寬條件（5,000 件的商品庫太小）；沒放寬的查詢 100% 滿足全部條件，有放寬的查詢平均只有 40% 的商品滿足**原始**條件，而且放寬了什麼都有寫進理由。
- 所有查詢都回傳滿 5 件。

| 設計要素（標準答案） | PRD 原版描述子 | 隨機字詞對照 | 反義詞成對＋分布正規化（新預設） |

| 休閒感（反向） | 0.718 | 0.638 | **0.981** |
| 低明度深色（黑、藏青…… vs 白、米……） | 0.839 | 0.484 | **0.981** |
| 鮮豔色彩（紅黃橙粉綠 vs 無彩色） | **0.884** | 0.466 | 0.848 |

表中是 Marqo 的數字；fashion-clip 的趨勢相同，隨機字詞對照在 0.33–0.70。

限制：
- 只有 4 個要素找得到不靠 CLIP 的標準答案。**肩線、霧面／亮面、領型、logo 這些 PRD 核心要素目前沒有驗證**，要靠 VLM 標註或人工標 40 件。
- 這 4 個要素都適用所有品類，所以適用性遮罩在這裡看不出效果。

### 3.3b PRD 核心設計要素的目視標註驗證（420 件盲標）
- **標註方式**：由 LLM 標註員逐張看圖，看不到任何模型分數，標籤只有 1／0／不適用。**不是人工標註**。
- **抽樣**：依 Marqo 反義詞分數的高／中／低三層各抽 20 件，對該評分方式可能稍微有利；fashion-clip 那組不受這個抽樣影響，趨勢一致。
- **檔案**：`data/labels/`（只存在本機），`scripts/eval_visual_labels.py`。

| 設計要素 | 正／負例 | PRD 原版描述子 | 隨機字詞 | 反義詞＋分布正規化 |
|---|---|---|---|---|
| 明顯 logo | 17／43 | 0.91 | 0.48 | **0.96** |
| 挺版領子 | 27／33 | 0.92 | 0.17 | **0.97** |
| 強烈圖案 | 20／40 | 0.85 | 0.36 | **0.90** |
| 寬鬆版型 | 7／47 | 0.84 | 0.65 | 0.86（CI 0.71–0.98） |
| 亮面材質 | 9／51 | 0.75 | 0.56 | 0.71（CI 0.52–0.89） |
| 肩線挺、柔軟針織 | **0 正例** | — | — | — |

表中是 Marqo-FashionSigLIP 的數字。

解讀：
- logo、領子、圖案用 CLIP 就夠準。
- **材質光澤不可靠**，跟 OVAD、MODA 的文獻一致。這一類要素要等 VLM 標註（`full_concept_vlm`）的結果。
- **KAGL 幾乎沒有西裝外套和針織衫**，所以「肩線挺」「柔軟針織」無法驗證，面試情境也沒有商品可推。已在 nycu 上把 Polyvore 服飾併入商品庫（`kagl_polyvore`）。

### 3.3c VLM 標註 vs CLIP（同一批 397 件的目視標註）

| 設計要素 | 正／負例 | CLIP（Marqo 反義詞＋分布正規化） | Qwen3-VL-8B（逗號分隔作答、讀選項機率） |
|---|---|---|---|
| 亮面材質 | 9／51 | 0.71（0.52–0.89） | **0.90**（0.80–0.98） |
| 明顯 logo | 17／43 | 0.96 | **0.98** |
| 挺版領子 | 27／33 | 0.97 | **0.98** |
| 強烈圖案 | 20／40 | 0.90 | **0.94** |
| 寬鬆版型 | 7／47 | **0.86** | 0.77（0.60–0.93） |

- **對 VLM 可能偏寬**：目視標註員也是 LLM，和 VLM 的判斷偏差可能相近。
- **VLM 標註第一版有 bug**：`BBB` 會被 BPE 合成一個 token，導致每題的機率對錯位置，已修正。修正後 397 件的答案格式 100% 正確。
- **混合模式** `full_concept_hybrid`：材質、logo、圖案、領子用 VLM，其他用 CLIP。

### 3.3d Encoder 比較（KAGL 5k，4090）
- 用詞相同的查詢，dense NDCG@5：Marqo-FashionSigLIP 0.614、zooclaw 0.612、siglip2 0.601、marqo-fashionCLIP 0.585、fashion-clip 0.569、LAION 0.537、OpenAI CLIP 0.499。

### 3.5d T6 隱性需求 vs 檢索品質的取捨（「在約束下維持推薦品質」）

設計要素權重 β_d 乘上 γ，對每句查詢隨機給 3 個需求機率，量三件事：
1. NDCG@5（屬性相符，同 T1）
2. 需求契合度：前 5 名的 Σ_d β_d·c(i,d)
3. 前 5 名相對 γ=0 被換掉的比例

| γ | 5k NDCG@5 變化（p） | 5k 換掉比例 | 44k NDCG@5 變化（p） | 44k 換掉比例 |
|---|---|---|---|---|
| 0.5 | −0.014（0.21） | 13% | −0.002（0.78） | 16% |
| **1（預設）** | **−0.027（0.06）** | **19%** | **−0.011（0.21）** | **26%** |
| 2 | −0.070（0.001） | 34% | −0.044（0.003） | 39% |
| 4 | −0.192（<0.001） | 49% | −0.107（<0.001） | 54% |
| 8 | −0.342（<0.001） | 67% | −0.193（<0.001） | 67% |

需求契合度從 γ=0.5 起每一檔都顯著上升（p<0.001）。

- **預設 γ=1 落在轉折點**：前 5 名有 19–26% 換成更符合隱性需求的商品，屬性相符度的下降不顯著。γ≥2 開始顯著犧牲品質。
- **商品庫越大，取捨越有空間**：同樣 γ=1，44k 的品質代價（−0.011）比 5k（−0.027）小。
- **限制**：NDCG 用屬性當標準答案，量不到需求本身。需求契合度是用我們自己的 K 表和 c(i,d) 算的，會偏向系統，只能當作「需求確實有影響排序」的證據，**不能當作「推薦更符合使用者需求」的證據**。

### 3.10 z-score 截斷（服務預設 `full_zclip3`）
- 商品池層級的 BM25 分布極度偏斜：大部分商品是 0 分，少數關鍵字命中的商品 z 值可以到 +7，壓過所有其他理由。
- 截斷在 ±3（100 句查詢，配對檢定）：

| 商品庫 | 用詞相同 NDCG@5（full → zclip3） | 換句話說 |
|---|---|---|
| KAGL 5k | 0.837 → 0.819（−0.018，p=0.036） | 0.099 → 0.197（p<0.001） |
| KAGL 44k | 0.814 → 0.808（−0.006，p=0.65） | 0.112 → 0.213（p<0.001） |

- 在接近真實規模的 44k 上幾乎沒有代價，而且卡片理由比較均衡，所以 API 與 demo 預設改用 `full_zclip3`。原本的 `full` 保留，先前所有數字都可重現。
- **但有一個可重現的邊界情況**（外部基準 sub-agent）：當查詢字面完全命中商品描述時，`full_zclip3` 的 Recall@10 一致低於 `hybrid_rrf`——KAGL −0.042、H&M −0.024、Polyvore −0.026（p≤0.0001）。機制很清楚：z 值被夾在 ±3 之後，榜首一堆商品同分。預設仍不改（真實查詢不是這種字面全命中），但**如果要對「貼上完整商品名稱」這種查詢做 demo，請改用 `hybrid_rrf`**。

### 3.12 偏好學習的抑制（T7b）
點一次就大幅改變排序會讓第二輪的理由被「你上一輪的回饋」主導。200 位模擬使用者 × 5 輪比較 6 種抑制方式：

| 設定 | 點 1 次後 \|Δβ\| 平均／最大 | 第 2 輪以回饋為首的理由 | 第 5 輪效用 |
|---|---|---|---|
| 原版 | 0.23／0.82 | 48%（5k）／53%（44k） | 基準 |
| **κ=1 縮減（Δβ·n/(n+1)，新預設）** | **0.11／0.41** | **36%／45%**（p<0.001） | −0.009～+0.023（p≥0.38） |
| κ=2 縮減 | 更低 | 更低 | 44k 小輸 0.04（p=0.038） |
| 縮小先驗 σ=0.3 | — | — | 明顯變差（−0.13～−0.17） |

κ=1 仍顯著勝過 PRD 的 ±1 規則（+0.07～+0.23，p≤0.033）。**比例下限**：需求平均分配時，連 PRD 規則都有 22–27% 的理由以回饋為首，再往下要在畫面呈現層處理。

1. **互補頭的分數是負距離**（實測約 −136.04 ～ −136.09），只在同一個品類格內可比較，**不能**跨格比、也不該直接顯示給使用者；卡片要排序用它，要顯示信心就用格內排名。

### 3.14b 補值商品庫上的端點驗收（cfda4，`kagl_polyvore_filled` 17,783 件）

驗收本身已經寫成 repo 內的腳本 `scripts/api_check.py`（在程式內直接跑 FastAPI app，不用起 port），會**斷言**而不是用眼睛看：貢獻加總等於總分、Div@k 對應實際卡片數、`feedback_violations` 等於兩個子項之和、滿足度用過濾器的同一把尺、否定詞會回報、商品自己的 embedding 最近鄰是自己、趨勢不進分數、錯誤錨點回 400。cfda4 上用 Marqo＋OT 實跑：15 項全過，`method=ot_cir`、slates 為 top×5／shoes×5。

### 3.15 趨勢關鍵字：量測後決定「不進排序」（T11，稽核 sub-agent）
PRD §6.6 要把趨勢關鍵字當小權重加分項。實際上 `set_trends()` 從第一版起就**沒有任何呼叫者**，所以過去所有數字都是「沒有趨勢項」的數字。補上並量測 28 組設定（3 種關鍵字來源 × 4 種權重 × 2 個商品庫 × 有無 z 截斷）後：**全部顯著變差**，NDCG@5 −0.16 ～ −0.38（p≈1e-4），手動維護清單只比隨機字詞好一點（44k −0.266 vs −0.301）。

**這個負面結果的適用邊界**（重要，否則會被拿去證明太多事）：`eval_trends.py` 的標準答案是商品屬性 metadata，所以**任何與那個標準答案正交的新項都只會扣分**——包含一個正確的趨勢先驗。§3.15 否證的是「熱門關鍵字進 BM25 式的分數項」，**不是**「所有趨勢訊號都無用」。要評估要素層級的趨勢先驗需要另一套有時間軸的標準答案（見 §3.26）。

決定：趨勢**只做展示標籤**（`trends.trend_badges()`），不進分數，代價 0；卡片照樣能寫「符合近期趨勢」。另外不接 Pinterest（開發者規範禁止儲存），關鍵字來源是手動清單或從策展穿搭推導，即時抓取的物件標記 `ephemeral` 且拒絕存檔。詳見 `docs/research/engine02-completeness.md` §3.1。

### 3.16 生成概念圖併入查詢：有效，已設為服務預設（T12）
情境是 PRD 生成分支被觸發的前提——**使用者講不出話**（模糊查詢，純文字 NDCG@5 只有 0.078/44k）。以保留法做替身實驗（目標商品自己的圖當「生成圖」，同時把目標放進 `excluded_item_ids`）：

| 概念圖來源 | w=0.2 的 NDCG@5（44k） | Δ vs 不用 | p |
| --- | --- | --- | --- |
| oracle（完美生成器上界） | 0.325 | +0.247 | 1e-4 |
| neighbour（方向抓對的現實生成器） | 0.278 | +0.200 | 1e-4 |

對照組是關鍵：隨機圖在同一權重下毫無幫助，所以那 +0.20 是資訊而不是「擾動查詢就會變好」。realistic ≈ oracle（0.278 vs 0.325）對生成分支是好消息。

同時修掉一個註解與程式不一致的 bug：`ArmConfig.z_clip` 寫的是截斷 dense/bm25/trend/penalty 四項，`pipeline._terms` 卻只傳給前兩項；現在四項都套用（趨勢項不進排序，實質影響的是第二輪的負例懲罰）。

### 3.18 感性對照表數值的敏感度（T13，KAGL 44k，60 句帶需求的查詢）
K[n,d] 的每一格都是從文獻編碼出來的判斷，沒有人工校準。與其宣稱數值準確，不如量「有多少結論依賴這些數值」：把所有非零格乘上 (1+ε)，ε～U(−noise, noise)，每個雜訊強度重跑 10 次。

| 擾動幅度 | 前 5 名重疊 | 前 20 名 Kendall τ | **卡片理由改變的比例** | NDCG@5 變化（第 5 百分位） |
| --- | --- | --- | --- | --- |
| ±20% | 0.959 | 0.909 | **51.5%** | +0.005（−0.019） |
| ±50% | 0.909 | 0.779 | **68.8%** | +0.000（−0.084） |
| ±100% | 0.831 | 0.627 | **78.5%** | −0.008（−0.170） |

解讀要誠實分成兩半：

- **推薦結果本身很穩**：就算把整張表的數值隨機拉動 ±50%，前 5 名仍有 91% 相同，檢索品質沒有系統性變化（平均 Δ≈0）。所以「K 表的數字要多準」不是這個系統的風險點——**方向（正負號與哪些格非零）才是**。
- **但使用者看到的理由會變**：±20% 就有一半的卡片改了被引用的理由（例如「深色沉穩」與「素面簡約」誰排前面）。理由永遠忠實於當下的分數分解，但不代表它在「另一份同樣合理的 K 表」下會是同一句。簡報要說的是「這句理由是這張表下的最小充分解釋」，不是「這是唯一原因」。

這也把 PRD 承諾的「GPT 多次取樣＋分歧格子人工校正」放到正確的位置：值得花時間校正的是**格子的正負與是否為零**，不是把 0.6 調成 0.65。

### 3.19 `full_concept_vlm` 消融，以及一個差點寫錯的結論（循環性）
補值商品庫上第一次跑得動 `full_concept_vlm`／`full_concept_hybrid`（T3）。第一版數字看起來 VLM 大勝：正式感 0.994 vs CLIP 反義詞 0.959、休閒 0.994 vs 0.959。**但那是循環的**——補值後的 `occasion` 正是同一顆 Qwen3-VL 填的，等於拿模型自己的答案當標準答案；同理 `color` 是用 Marqo embedding 上的 probe 填的，會反過來偏袒 CLIP 系的分數。

修法：`concept_labels()` 現在會依 `attr_source` 把**模型補值的欄位剔除**，只用資料集原生標籤（3,287 件）。乾淨重跑後：

| 設計要素 | CLIP 反義詞（`full`） | VLM（`full_concept_vlm`） | 隨機字詞對照 |
| --- | --- | --- | --- |
| 正式感 | **0.982**（0.976–0.987） | 0.974（0.964–0.982） | 0.528 |
| 休閒感 | **0.982**（0.977–0.987） | 0.974（0.964–0.982） | 0.633 |
| 深色調 | 0.981（0.975–0.987） | 0.982（0.976–0.987） | 0.487 |
| 鮮豔色彩 | **0.849**（0.832–0.867） | 0.812（0.792–0.832） | 0.466 |

**結論翻轉**：在乾淨標籤下，VLM 在這四個要素上**沒有**勝過 CLIP 反義詞打分（顏色類還明顯較差）。所以維持現狀——`full`（反義詞）是預設，VLM 只用在 §3.3c 用目視標註測出它真的比較強的材質／光澤／logo／領子／圖案那幾項（`vlm_elements`）。`full_concept_hybrid` 因為只替換那幾項，在這張表上與 `full` 完全相同，符合預期。

這也是為什麼補值商品庫上的每一個評估都要問一句「標準答案是不是我自己填的」。`concept_labels(allow_predicted=True)` 可以還原舊行為，但預設不該用。

### 3.19b LLM 改寫的幻覺率：不需要 API key 的量測方式
組員能用的是 ChatGPT 介面裡的 agent，不是 API，所以原本「接上 key 就能測」的路走不通。改成貼上式流程，量到的東西完全一樣：

1. `python scripts/eval_llm_paraphrase.py export --catalog ... --n-queries 20` → `prompts.jsonl`（機器可讀）＋ `paste_me.txt`（每批 10 張卡的事實 JSON，附固定輸出格式的指示）。送進 agent 的**就是** pipeline 會送的那份 JSON，沒有另外美化。
2. 組員逐批貼上，把回覆原樣存成一個文字檔（`<id> | <句子>`；JSONL 也吃）。
3. `... score --responses <檔案>` → 用**產品裡同一個** `verify_paraphrase()` 判斷，輸出通過率、被擋原因（捏造數字 vs 捏造設計要素標籤）、字數分布，以及每一句被擋的原文與冒出來的那個 token。

另外補了一個 `verify_paraphrase()` **抓不到**的失敗模式：**極性反轉**。把「避開明顯 logo」寫成「很有明顯 logo」時，標籤本來就在事實裡、數字也沒錯，所以事實檢查器會放行，但意思完全相反（這正是先前模板理由踩過的 bug）。因此 (a) 批次指示明講 `has` 與 `avoids` 的差別，(b) 評分時會把「提到 avoids 要素卻前面沒有否定詞」的句子標出來給人看——這是**啟發式提示，不自動判錯**。

合成測試（故意放一句寫「+9.99」、一句寫 JSON 裡沒有的「運動機能風格」、兩句把 avoids 反寫成具備）四種都被抓到，沒回覆的卡片也會列出來。目前已備好的正式題本是 **100 張卡（20 句查詢 × 5 件，Marqo＋補值商品庫，分 10 批）**，在 `reports/llm_paraphrase/paste_me.txt`。要記得在簡報上講清楚的是：**被擋不等於系統出錯**——卡片會退回模板，使用者永遠看不到那個捏造的事實；要報的數字是「退回率」。

### 3.21 即時性：把 298 ms 的 `/rank` 壓到 12 ms（現場是 live demo）
現場流程是「評審出題 → 看結果 → 給回饋 → 再出題」，所以延遲屬於評分項（呈現完整度 20%）。實測與優化都在 `scripts/bench_latency.py`、研究依據在 `docs/research/serving-latency.md`。

| 端點（cfda4，V100 級 GPU，Marqo-FashionSigLIP） | 優化前 p50 | 現在 p50 | 現在 p95 |
| --- | --- | --- | --- |
| `/rank`，`kagl_polyvore_filled` 17,783 件 | 298 ms | **12.8 ms** | 14.1 ms |
| `/rank`，`kagl_full` 44,434 件 | — | **15.7 ms** | 19.7 ms |
| `/view`（排序＋所有面板） | — | 12.5 ms | 14.4 ms |
| `/complete-look`（OutfitTransformer 互補頭） | 554 ms | **33.3 ms** | 87.8 ms |

**四個瓶頸沒有一個是模型**，全部是「離線該做的事被放到線上做」：

1. `attr_source` 逐列 `json.loads`（五次請求 711,345 次呼叫，約 0.6 秒/請求）→ 每個商品庫只解析一次；

3. 槽位比對每次 `Series.map(_norm)`（每槽位 × 每放寬階梯各一次）→ `engine02/attrindex.py` 整數碼＋布林查表；
4. 規則指標每張卡建一個 1 列 DataFrame（連 AttrIndex 都被重建 220 次）→ 全庫遮罩算一次再索引。

另外：BM25 改成掃 postings（`rank_bm25` 是「每個查詢詞掃全庫」，同一公式、逐分相同，`tests/test_sparse.py` 對照驗證）、dense 不再把 float32 升型並複製候選池、卡片欄位改成位置索引的 numpy 視圖、OutfitTransformer 的商品 embedding 離線預算（17.8k 件 1.3 分鐘、73 MB）。

**每一項都必須證明沒改變排序**：`scripts/check_parity.py` 在 60 句查詢上比對前 20 名 id，float32 路徑與 float64 完全相同（最大分數差 1.3e-06）；T1/T2 消融也重跑對照。

**現場風險的處置**（都已實作，不是計畫）：啟動時自動暖機一次查詢（含一次 complete-look），`/health` 回報 `warm_ms`；LLM 改寫每次呼叫 timeout 2 秒、不重試，**每個請求共用 1.5 秒總預算**且第一次失敗後整輪退回模板（原本 SDK 預設 600 秒＋重試 2 次，斷網會讓每張卡各等一次）；`ENGINE02_DEMO=1` 直接禁用 LLM 路徑，客戶端無法覆寫。

**刻意不做**（依 `docs/research/serving-latency.md` 的量測與文獻）：不加 ANN（17.8k 精確 matvec 只要 1.4 ms，Faiss 官方建議 <1M 不需要 IVF）、不加 roaring bitmap（17.8k 位元的 numpy AND 是 5 µs）、不用 mmap 載 embedding（只是把成本搬到第一個真實查詢）、不加查詢結果快取（評審每輪改條件，命中率近 0，還會製造「改了條件卻回一樣卡片」的舞台 bug）。

### 3.22 設計要素的需求–供給缺口盤（T14；給製造商的那一頁）
這是唯一「只有製造商評審會在意、而且只有 ENGINE 02 算得出來」的輸出：需求側把每次查詢的 β_d 聚合（**正負分開、不相消**），供給側算目錄中 c(i,d) > τ 的比例，`Gap = |需求佔比| × (1 − 供給)`（想避開的要素則乘供給）。端點 `GET /gap/elements`、`GET /gap/cells`，需求側就是本服務實際收到的查詢，每份回應都寫明分母。

**可否證的驗證**（`scripts/eval_gap.py`，KAGL 44k、真 encoder、45 次試驗）：

| 條件 | 該要素在缺口榜的 MRR | 排第一的比例 |
| --- | --- | --- |
| 原始目錄 | 0.381 | — |
| **遮掉表現該要素的商品** | **0.509** | 28.9% |
| 遮掉同樣件數的隨機商品（對照組） | 0.380 | 15.6% |

注入 vs 對照 **p < 1e-4**；對照 vs 基線 **p = 1.00**（隨機移除完全不動缺口排名）。所以這個指標是在回應「特定要素的供給」，不是在回應「目錄變小」。第一版實驗設計是錯的——只給單一要素需求時它永遠排第一、三種條件完全相同，等於什麼都沒量到；改成需求分散到多個要素才有鑑別力。

**這個驗證不能宣稱什麼**：它沒有證明缺口能預測真實銷售。需求側是我們自己的查詢分布，所以它量的是「這個目錄被問到什麼」。

### 3.23 第二輪會不會只是重播第一輪？（T15）
`ChoiceRecord.shown_item_ids` 一直存在，但排序從來沒讀它。實測證實了最糟的情況：**不處理時，第 4 輪的新穎度是 0.007**——評審給了回饋，但畫面幾乎是同一批卡片。

審查這一項時發現三個問題，第一個直接違反我們的核心主張：

1. **它在卡片上是隱形的**。`template_reasons` 只引用正貢獻，`GROUP_LABEL` 也沒有這一組，所以它改了排序、系統卻說不出來——在一個賣「解釋＝分數分解」的產品裡，這是自打嘴巴。
2. **它自稱「隱性負回饋」，也就是一個口味主張**。但「沒被選」＝「沒看到」∪「看到但不喜歡」，一個 session 的約 20 次曝光**無法分離**這兩件事；而口味這件事偏好學習器已經用選擇概似（MNL／Bradley–Terry，對整個被展示集合）做得更好了。
3. **每張被忽略的卡權重相同**。排在第 5 的商品可能根本沒被看到。

**修正後的形式**：正向表述的「新鮮度」項，`raw = 1 − 曝光量`，權重為正。沒看過的商品得到 +w 且卡片可以寫「這件你這輪還沒看過」；已經有效看過的是 0 或負。這和原本的懲罰項**排序等價**，但說得出口——「因為你沒選它」是資料撐不住的指控，「你還沒看過這件」是事實。曝光量依**已發表的眼動注視機率**加權（Joachims et al., SIGIR 2005，29 位受試者）：ε = (1.00, 0.85, 0.71, 0.47, 0.37)，刻意用查表而不是冪次律，因為注意力在第 1–3 名幾乎持平、在第 4–5 名斷崖。使用者整輪沒選任何一件是 outside-option 事件，只計 0.5 倍（先前它是被當成最強證據）。

**T15（KAGL 44k、Marqo、60 個模擬使用者、4 輪）**：

| w | 最後一輪新穎度 | p | 平均效用 | p | **最佳卡片效用** | p | 找到目標 | p |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 0（關閉） | 0.007 | — | 2.581 | — | 3.636 | — | 0.933 | — |
| 0.15 | 0.167 | <1e-4 | 2.619 | 0.50 | 3.772 | 0.031 | 0.917 | 1.00 |
| **0.50（採用）** | **0.237** | **<1e-4** | 2.543 | 0.59 | **3.811（+0.18）** | **0.008** | 0.900 | 0.50 |

新穎度提升而效用**沒有**顯著下降，而且**整排最好的那一件反而變好**（+0.18，p=0.008）：把重播的位置讓出來，系統就得去拿它原本壓在後面的商品。服務預設 arm `full_zclip3` 採用 w=0.5，對照組 arm 是 `full_zclip3_nofresh`。

### 3.25 「保證不重播」的硬規則：實作了、量了、決定不開（T15-B/C）
分數項無法**保證**榜首會換——實測第 1 名與第 6 名的分數差約 0.5，任何撐得住的權重都跨不過去。所以另外實作了一個位置加權的**頻次上限**（累積一次完整有效曝光就把該商品移出候選池），它是規則、不需要估計器。結果是它不該當預設：

| 設定 | 最後一輪新穎度 | 平均效用 | p（效用 vs 關閉） |
| --- | --- | --- | --- |
| w=0.5，無上限（**採用**） | 0.237 | 2.543 | 0.59 |
| w=0.15 ＋ 上限 | 0.410 | 2.229 | **0.0004** |
| w=0.5 ＋ 上限 | 0.363 | 2.313 | **0.0066** |
| w=0.5 ＋ 上限，**平權曝光**（不用眼動權重） | 0.800 | 2.094 | **<1e-4** |

**兩個結論**：(a) 硬上限買到很多新穎度，但顯著傷害使用者實際拿到的東西——它會把使用者**只是還沒看到**的商品也趕走；(b) **眼動加權是有價值的**：同樣權重下改成平權曝光，新穎度衝到 0.80 但效用掉到 2.094，遠差於加權版的 2.313。排名權重保護的正是「使用者大概根本沒看到」的那幾件。

上限仍保留在程式裡（`ArmConfig.exposure_cap`，預設 0＝關閉），若有人要求「絕對不重複」的硬保證再打開；而且它**永遠不會把候選池清空**，被迫跳過時回應裡會寫 `exposure_cap_skipped`，不會默默重播。

### 3.24 上傳的照片能不能相信？（T16，域差與要素側寫的穩定度）
`/visual-search` 與概念圖融合都建立在一個假設上：**使用者上傳的照片會落在目錄圖片所在的那塊 embedding 空間**。§3.16 已經把這件事列為「正結果只是上界」的原因，現在把它量出來。DeepFashion-InShop 的同一件衣服同時有模特兒照（`_1_front`／`_2_side`／`_3_back`）與平拍照（`_6_flat`，最接近目錄商品照），這是受控的代理。

**檢索**（677 件衣服，索引只放平拍照）：

| 查詢 | R@1 | R@10 | MRR |
| --- | --- | --- | --- |
| 模特兒正面照 → 平拍照（域差） | **0.601** | 0.892 | 0.705 |
| 另一個模特兒視角（側／背）→ 平拍照 | 0.502 | 0.866 | 0.632 |
| 另一張平拍照 → 平拍照（同域對照） | **無法取得** | — | — |

同域對照組是 **n=0**：這份語料裡沒有任何衣服有兩張平拍照，所以這個數字**無法分離「域差」與「任務難度」**。第一版腳本在這裡有個 bug——只有一張平拍照時，對照查詢退化成拿目標自己當查詢，R@1 必然 1.0；**一個不可能失敗的對照組不是對照組**，已修並改用「另一個模特兒視角」來至少分離「換一張照片」與「換一個域」。

**要素側寫的一致性**（150 件 × 15 要素，同一件衣服的兩種拍法）：

| 比較對象 | 平均 \|Δz\| | Pearson | **正負反轉率** |
| --- | --- | --- | --- |
| 平拍 vs 模特兒（同一件） | 0.366 | 0.78 | **9.7%** |
| 平拍 vs 不同衣服（對照） | 0.95 | −0.003 | 41.1% |

所以側寫整體是有訊息的（r=0.78，遠離隨機對照），但**每十個要素就有一個會講反**。最不穩的是版型（0.585）、材質光澤（0.496）、領型（0.493）——全都依賴垂墜與打光；最穩的是深色調（0.205）、針織（0.234）、正式／休閒（0.240）。

**處置（不是改進模型，是改進誠實度）**：這張量測表隨套件出貨（`engine02/resources/profile_stability_v1.json`），`concepts.element_profile` 每個要素回傳 `stability_abs_delta_z` 與 `reliable`（沒量過的回 `None`——**沒量過不等於穩定**），`/visual-search` 會把不穩的要素列出來並標「只當參考不要當事實」。

**這個數字是下界，而且已發表的文獻告訴我們低估了多少**：兩邊都是零售商的攝影棚照片。真正的「買家實拍 → 店家照」是另一個量級——**FashionNet 在同一篇論文裡，店內檢索 top-20 是 76.4%，買家照→店家照只有 18.8%**（DeepFashion, CVPR 2016；論文自己寫「reflect the inherent difficulty of consumer-to-shop clothes retrieval」）。到 2019 年店內任務已接近飽和（R@20 98.5%），買家照仍只有 top-20 64%（GRNet, ICCV 2019）；DeepFashion2 的 Match R-CNN 在**給定正確框**的條件下 top-20 66.5%，用偵測框則掉到 61.7%。

所以現場要講的話是：**「以圖找同款」這件事本身在文獻上就沒有解決**，我們的 0.601 是在最有利的條件下量到的上界。這也是為什麼 `/visual-search` 的重點放在**回傳設計要素規格**而不是宣稱找到同款——規格是我們量過穩定度的東西（並且會標出哪幾項不可信）。

### 3.26 KOL／社群訊號：機制可行、訊號不可行（決定不做，並說得出為什麼）
組內提案：IG／X 上的 KOL 引領潮流，把他們的貼文當推薦系統的輸入。這個方向**在業界是真的**，但查證後的結論是**不要做**，而且理由夠硬，值得主動講。

**① 產業龍頭自己把答案公布了。** Heuritech（分析社群影像做趨勢預測，客戶為精品品牌）發表了 HERMES 資料集與模型（arXiv:2202.03224，作者含 Heuritech），公開 10,000 條週頻時尚趨勢序列，**每一條都附一個「influencer 行為」的外部弱訊號**——正是這個提案的產業實作版。他們自己報告的 MASE 改善：

| 序列數 | TBATS 基線 | HERMES ＋ influencer 訊號 | 相對改善 |
| --- | --- | --- | --- |
| 10,000 | 0.745 | 0.7132 | −4.3% |
| 1,000 | 0.734 | 0.7151 | −2.6% |
| **100** | 0.745 | 0.7368 | **−1.1%** |

而且論文寫明那個訊號是**稀疏的**，要靠跨數千條序列 pooling 的全域 RNN 才萃取得出來。**我們折疊反義極之後只有 11 條正規軸**——所以這不是「資料不夠」，是機制上不可行。

**② 原始社群影像合法拿不到**（存取日 2026-09-18）：Instagram 需 App Review 且限「30 個 hashtag / 7 天」，Meta 平台條款要求不需要時即刪除；TikTok Research API 限特定地區的學術機構；X 已改為用量計價且找不到學術層；Pinterest 條款逐字寫明「you may not store any information accessed through any Pinterest Materials including the API」（這正是我們既有 `trends.from_live_fetch` 標記 `ephemeral` 的原因）。唯一能合法儲存影像的是 Flickr 的 CC 授權內容。

**③「KOL 引領、大眾跟隨」的強版本學術上不被支持**：Watts & Dodds（JCR 2007）發現擴散「driven **not by influentials** but by a critical mass of easily influenced individuals」；Goel et al. 指出大型擴散是**廣播**而非逐層滲透；Shalizi & Thomas（2011）指出同質性與傳染在觀察資料中**一般不可辨識**；Leung et al.（J. Marketing 2022）量到的是**互動**不是銷售，而且「宣告新品上市的貼文反而降低互動」。另外一個常被引用的正面結果（Rudna et al., 2026）對照組是「univariate baseline」而非 persistence/seasonal naive，RMSE 3.47 vs 91,034 差四個數量級——那是基線在非定態序列上爆掉，不是方法變好。

**④ 還有一個結構性風險**：KOL 貼文多為業配，反映的是**品牌過去的決策**，把它當「消費者需求」會讓我們把品牌自己的決定回灌成需求訊號。

**我們因此做的事，是把介面留好而不是把訊號做出來**：`Engine02Request.design_weight_prior`（設計要素 → 權重）接受**外部**先驗——企劃的指示，或**主辦方自己已經在跑的趨勢平台**的輸出。它走同一個可加總欄位，但在卡片上**分開歸因**（「外部趨勢／企劃偏好（非你本人的輸入）」），並且被**夾在一格使用者回饋的幅度內**（`KanseiTable.step_size = 0.25`），所以族群訊號在代數上永遠壓不過眼前這個人。

**現場可以這樣講**：「趨勢關鍵字進排序我們量過，28 組全部變差（§3.15，注意那個實驗的邊界）。所以我們沒有自己做趨勢預測器——不是做不到，是這個產業的龍頭已經公布過答案：Heuritech 用 10,000 條序列加 influencer 訊號只換到 4.3% MASE，100 條時只剩 1.1%。我們只有 11 條軸。我們做的是把貴公司**既有趨勢平台的輸出**接進來的位置：有上限、有歸因、使用者永遠壓得過它。」

### 3.27 查詢端正規化：文獻上最強的一招，在我們的資料上量不出效果（T17，null result）
T16 量到域差之後，最自然的下一步是文獻裡效果最大的那一招：**把查詢裁切到衣服本身**。Street2Shop（ICCV 2015）用物件提議取代整張圖，top-20 從 10.1→42.0（眼鏡）、11.6→45.9（裙子）、14.4→27.4（上衣）；Alibaba（KDD 2018）還證明粗糙的弱監督框在下游幾乎不損失（Recall@1 46.5 vs 46.7）且快 3 倍；每個上線的視覺搜尋系統都做 detect-and-crop。另外「**只對查詢去背、索引不動**」這個組合在文獻上查不到，而那正是 `/visual-search` 的處境。

所以跑了 T17（400 件衣服，模特兒照 → 自己的平拍照，**索引完全不動**，`u2net`／Apache-2.0）：

| 查詢端處理 | R@1 | R@10 | MRR | ΔR@1 | p |
| --- | --- | --- | --- | --- | --- |
| 不處理（現況） | 0.625 | 0.915 | 0.731 | — | — |
| 中央裁切 70% | **0.652** | 0.938 | 0.753 | +0.028 | 0.054 |
| 裁到顯著物件外框 | 0.615 | 0.922 | 0.725 | −0.010 | 0.51 |
| 去背合成白底 | 0.640 | 0.910 | 0.746 | +0.015 | 0.21 |
| 去背＋裁切 | 0.605 | 0.912 | 0.716 | −0.020 | 0.25 |

**沒有任何一種達到顯著**，而且用模型做的分割**沒有贏過一個什麼都不用的中央裁切**。

**為什麼和 Street2Shop 差這麼多——這才是重點**：Street2Shop 的巨大增益來自**移除街拍的雜亂背景**，而我們手上唯一能做這個實驗的語料（DeepFashion In-shop）兩邊都是**攝影棚照片**，本來就沒有什麼背景可以移除。所以這不是「裁切無效」的證據，而是**我們的代理實驗裡沒有那個機制可以作用**。

**決定**：不因為這個結果把裁切／去背加進產品。加一個相依（rembg 的預設模型 **BRIA RMBG-1.4 商用要付費授權**，我們釘的是 `u2net`）與一條程式路徑，卻沒有量到好處，違反這個專案其他每一個決定的標準。腳本留著當證據（`scripts/eval_query_norm.py`），並記下**真正能回答這題的實驗需要街拍查詢**——而那正是 §3.26 說明的、合法拿不到的資料。

順帶一提，同一份研究也指出三條**不要走**的路：查詢擴展／DBA／diffusion 在「每個查詢只有一個正解」的情境會**變差**（Revisiting Oxford/Paris 明寫 degrade queries with few relevant images，我們正是這種）；k-reciprocal 重排的招牌 +14.6 是 mAP，Rank-1 只有 +3.5，而我們的產品指標是前 5 張卡；白化／域均值相減的量級只有 1–4 分且**方向與任務有關**，不能假設縮小 modality gap 一定比較好。

### 3.28 文字 cross-encoder 重排：第三次否決重排器（T18）
先前只測過**影像** reranker（Qwen3-VL-Reranker-2B，變差且慢）。文字版從沒測過，而它是當時唯一還沒被否證、能直接動到 NDCG 的選項，所以補測（`kagl_polyvore_filled` 17,783 件、60 句查詢、Marqo）。

對照組是服務預設 arm `full_zclip3`（NDCG@5）：

| 重排器 | 用詞一致 | p | 換句話說 | p | 每次查詢延遲 |
| --- | --- | --- | --- | --- | --- |
| 無（`full_zclip3`） | 0.759 | — | 0.130 | — | 13.8 ms |
| bge-reranker-v2-m3 | 0.762（+0.003） | 0.91 | 0.067（**−0.064**） | **0.0001** | **582 ms**（42×） |
| Qwen3-Reranker-0.6B | 0.749（−0.010） | 0.72 | 0.085（**−0.045**） | **0.0016** | **3,061 ms**（222×） |

**三件事一起否決了它們**：該幫忙的地方沒有效果（p=0.72／0.91）、在我們最弱的情境**兩個都顯著變差**、而且把 13.8 ms 的查詢變成 582 ms 與 3,061 ms，直接毀掉現場的即時性。

**為什麼會這樣（機制解釋）**：我們的「文件」是商品標題，短到 cross-encoder 幾乎沒有東西可以推理——它能用的訊號和 BM25＋dense 已經抓到的重疊；而它對字面重疊敏感，等於把我們刻意壓下去的 lexical bias 再放回來，所以換句話說的查詢受害最重。

連同先前的影像版，這是第**四**個被否決的重排器（影像 2B 變差、影像 8B 官方路徑跑不通、文字 m3、文字 Qwen 0.6B）。**結論是穩定的：在這個任務上，重排器不是缺的那一塊**——缺的是 ENGINE 01 的詞彙正規化（§3.1）與商品屬性的完整度（§3.17）。

### 3.29 修好一條壞掉的降級路徑：換句話說的查詢從 0.111 到 0.308（T19，**已上線**）
§3.1 一直記著這個弱點：換句話說的查詢，純 dense 是 0.328，而所有混合 arm 落在 0.067–0.150。這一輪把它**診斷到根因並修好**。

**根因不是「BM25 算不到分」，是 idf 病理。** 換句話說的 60 句裡，BM25 第 1 名有 **37 句是被 `everyday` 推上去的——那個字在 5,000 件商品中只出現在一件的標題裡**（df=1、idf 8.11，全句最高）；加上 `workout`（df=2）就是 49/60。`emerald` 甚至把第一名給了一支 Revlon 眼線筆。所以 0.034 比隨機還差：排序被**系統性推向反相關商品**。

**所以既有的閘門才從不觸發**：`coverage` 問的是「這個詞在不在商品庫詞彙裡」，而 `everyday`／`jet`／`emerald` **都在**——換句話說的查詢覆蓋率仍有 0.85（我們的門檻是 0.5），**93% 的違約查詢直接通過**。

`ground_query()`（`engine02/taxonomy.py`）把使用者寫的字改寫成商品庫真正用的詞（「大學T」→ `Sweatshirts`），
只作用在庫內的服裝節點上。`docs/research/paraphrase-robustness.md` 記的是**大幅正向**（換句話說 0.186 → 0.601）。

| --- | --- | --- |
| `full_zclip3`（服務預設） | **0.7338** | **0.3080** |

### 3.31 具名分面：同一份排序，讀出三種意思（`POST /facets`，**已上線**）

靈感來自 **GenFacet（SIGIR 2026，JD.com 已上線，線上 facet CTR 相對 +42.0%）**，但**我們不做它的方法**：
我們的分面不用生成，11 條設計要素軸（§3.3，每一條都有 AUROC 證據）本身就是具名、可稽核、每件商品都有分數的面向。

**關鍵設計決定：這是面板，不是重排序。** 排序、分數、每一項貢獻都原封不動，
所以 §3.1–§3.29 的檢索數字**一個都不用重跑**，分面也不可能講錯分數。
`tests/test_silent_failures.py::test_facets_do_not_change_the_ranking` 把這件事釘住：
每件商品恰好落在一群、沒有憑空多出商品、問過分面之後再排一次結果逐位元相同。

**軸怎麼挑**（三個乘數，每一個都是為了擋掉一種假分面）：

| 乘數 | 擋掉的假分面 |
| --- | --- |
| 在結果內的離散度 | 所有商品在這條軸上都一樣 → 切了也沒有差別 |
| ×(1 − 與分數的相關性) | 這條軸只是把分數換句話說 → 使用者得不到新資訊 |
| ×(1 − 與品類的 Cramér's V) | 「切分」其實是在分手提包和襯衫 → 那是品類清單不是讀法 |
| ×平衡度（最小群 ÷ 均分） | 49 對 1 的切分 → 一件離群商品假扮成一個分面 |

實測（KAGL 44k、50 件候選、15 條軸）：**2.7 ms**，而且是獨立呼叫，不佔 `/rank` 的 12.8 ms 預算。
群數 2–3 由資料決定（群太小或兩個質心疊在一起就降一群）。
一次實際輸出：查詢「a shirt for an interview」→ 軸「素面簡約 ↔ 強烈圖案」，
切成 4／27／19 三群，與分數相關性 0.00、與品類關聯 0.00。

**誠實限制**：GenFacet 的 +42.0% 是**線上 CTR**，不是離線檢索品質。它支持的命題只有一個——
「把結果切成具名分面端出去，人的反應會不一樣」——**不能拿來宣稱我們的 NDCG 會變好**（我們根本不動 NDCG）。
`category_confound` 高於 0.5 時，回應會自己在 `note` 裡說「這個切分有一部分其實是在分品類，請照這個數字打折看待」。

### 3.32 開場三題：把第一輪從「零個人化」變成「有先驗」（`/profile/questions` + `/profile`，**已上線**）

**問題**：目前第一輪完全沒有個人化——β₀ = γ·p(n)·K 只由 ENGINE 01 那句話決定。
我們有貝氏成對偏好學習（§3.12），但它要有回饋才會動，第一輪沒有回饋。

**做法**：上台前先讓評審點 3 次照片（不是打分、不是形容詞），每題兩張**真實商品**分居某條設計軸的兩端。
軸的挑法：依商品庫在該軸的離散度排序，並跳過與已選軸相關性 > 0.5 的軸——三題問同一件事等於只問了一題。
選項是**服裝**、且取第 2／98 百分位而不是極值（混合商品庫裡「最正式」的那一列可能是一支口紅）。

**它進分數的方式，以及為什麼不會綁架後面幾輪**：
權重 = `κ₀ / (κ₀ + 已發生的回饋輪數)`，κ₀ = 3（等效樣本數上限），再乘上既有的 `step_size` 上限。
也就是說**第 3 輪之後，使用者真正做過的事一定壓過開場那三題**——這是一個有上界、可被測試檢查的性質，
不是一句「不會影響太多」的保證（`tests/test_silent_failures.py::test_profile_is_a_prior_that_real_feedback_outvotes`）。

**歸因是分開的**：它走 `Engine02Request.profile`，不是 `design_weight_prior`——後者的卡片文案寫死是
「外部趨勢／企劃偏好（非你本人的輸入）」，拿來講使用者自己的選擇是**錯誤歸因**。
`profile` 的卡片文案是「你開場挑的偏好」，與本輪打的字分開列在同一張卡上。

**為什麼是 3 題**：Zou et al.（SIGIR 2020）實測偏好誘導「在前 10 題內就達到很好的表現」，
真人平均答 15 題、每題中位數 5 秒。**所以 3 不是文獻結論，是舞台決定**——3 題約 15 秒才塞得進
`docs/engine02-pipeline.md` §9 的 30 秒／段腳本。另一個獨立論證：二選一最多 1 bit、設計軸有 11 維，
3 題連一半軸的正負號都定不了——**數學上它只能當先驗，不能當結論**，這正好對上 κ=1 縮減的設計意圖。

**對照實驗跑完了**（`scripts/eval_profile.py`，200 位模擬使用者、`kagl_polyvore_filled`、marqo、
第一輪、無任何回饋、目標商品在前 50 名內、配對排列檢定 20,000 次；`reports/server/profile/`）：

| arm | 第一輪 MRR | hit@5 | vs 無側寫 | vs `p3_shuffled` |
| --- | --- | --- | --- | --- |
| 無側寫 | 0.0143 | 0.025 | — | — |
| **p3（3 題，照實答）** | **0.0239** | 0.030 | **+0.0096（p=0.0003）** | **+0.0024（p=0.0076）** |
| `p3_shuffled`（同樣答案打亂配對） | 0.0215 | 0.025 | +0.0072（**p=0.31，不顯著**） | — |
| `p3_rand`（隨機作答） | 0.0215 | 0.025 | +0.0072（p=0.38） | −0.0000（p=0.81） |
| p5（5 題） | 0.0276 | 0.030 | +0.0133（p=0.0005） | +0.0061（p=0.0019） |
| p10（10 題） | **0.0358** | 0.045 | **+0.0215（p=0.0003）** | +0.0143（p=0.0010） |

**三個結論，其中兩個對我們不利，必須照講**：
1. **側寫的內容確實有作用**：p3 同時打敗「無側寫」與「自己的洗牌版」（p=0.0076），功能存活。
2. **但大部分的表面增益不是內容**：p3 對無側寫的 +0.0096 裡，有 **+0.0072 被洗牌版複製**，
   而洗牌版對無側寫**本身並不顯著（p=0.31）**——也就是說真正屬於「你答了什麼」的部分只有大約四分之一。
   宣稱「開場三題就懂你」是誇大，正確說法是「三題買到一點點方向，而且我們量得出它有多少」。
3. **3 題確實留了價值在桌上**：10 題是 +0.0215，是 3 題的兩倍以上，與 Zou et al.（SIGIR 2020）
   「10 題內收斂」一致。**3 是舞台時間預算的選擇，不是最佳點**，簡報要這樣講。

**這個實驗最寬鬆的假設**：模擬使用者是「照實回答」的，也就是最有利的情況；真人會答錯、會猶豫。
另外 MRR 的絕對值很小（17,783 件中用一句很模糊的話找一件指定商品），所以相對增益是建立在很小的基數上。

### 3.34 連外部訊號的方式：側車，不是請求路徑（`scripts/fetch_context.py` + `GET /context`）

**要求**：系統最好能連網擴充（天氣、外部趨勢平台、贊助商系統）。
**限制**：從台北冷連線 Open-Meteo 實測 p50 **1.57 秒**（光 TLS 握手就 0.95 秒），暖連線 0.295 秒，
而 `/rank` 是 **12.8 ms**、每請求預算 1.5 秒；而且 `ENGINE02_DEMO=1` 的服務路徑本來就沒有網路。

**做法（兩者都要）**：
1. **抓取在服務路徑之外**：`scripts/fetch_context.py` 連網一次（或 `--every 900` 當背景更新器），
   寫成 `data/context/weather.json`。Open-Meteo 免金鑰、10k/日、資料 CC-BY-4.0（2026-09-18 查證）。
2. **服務路徑只讀本地檔**：`GET /context` 回傳情境、**它有多舊**、以及呼叫端**可以**附上的
   `constraints.season = {state:"inferred"}`。檔案不存在或過期**不是錯誤，是文件寫明的 no-op**。

**兩條刻意的界線**：
- **ENGINE 02 不會自己附上季節**。季節是呼叫端對使用者的判斷，不是我們的。
- **它不是分數項**。`inferred` 的 slot 不進硬過濾（`Slot.is_hard()` 回 False），只進檢索句，
  實測候選池 5,000 → 5,000、放寬清單為空（`tests/test_silent_failures.py::test_context_never_shrinks_the_candidate_pool`）。

**為什麼不做成天氣加分項**：§3.15／§3.26／§3.27／§3.28／§3.30 同一條標準——不能量的東西不能上。
`docs/research/context-weather-recsys.md` 量到本商品庫的 `season` 不是體感季節
（756 件 Winter 裡有 294 支手錶、144 副太陽眼鏡，毛衣的 Winter 是 0），
所以天氣分數項在這份資料上**無法被驗證**。管線先接好、誠實標示；
換到有材質與厚度欄位的贊助商商品庫，`c(i, thermal)` 這條軸的成本仍近乎零。

### 3.33 批評的三個具名角色：量了，有效，**已上線**（T8 重跑，600 triplet）

「這件，但換成海軍藍」在文獻裡是一個融合向量（CLIP4Cir 的 α、TIRG 的殘差）。
融合之後那個 α 是黑盒，卡片上講不出任何一句話。
**MulVec（arXiv:2608.25305, 2026）的角色拆分**指出同一句批評其實是三個陳述，我們把它做成三個具名項：

| 角色 | 分數 | 卡片上長什麼樣 |
| --- | --- | --- |
| 你要出現的 | `+w · sim(商品, txt("navy blue shirts"))` | 「你要的海軍藍 +1.29」 |
| 你要保留的 | `+w · sim(商品, img(參考商品))` | 「和你指的那件相近 +0.88」 |
| 你要消失的 | `−w · sim(商品, txt("black shirts"))` | 「你不要的黑色 −0.82」 |

三項仍然**精確加總等於總分**，可加總不變式沒有被破壞。

**實測**（`scripts/eval_composed.py`，KAGL、marqo-fashionSigLIP、600 triplet、test 半邊 n=600，配對排列檢定 20,000 次）：

| 比較 | ΔNDCG@10 | 95% CI | p |
| --- | --- | --- | --- |
| 現行 `critique_filter` **＋三角色** | **+0.0635** | +0.047 ～ +0.081 | **0.00005** |
| ↳ 只看換顏色 | **+0.1057** | +0.075 ～ +0.139 | 0.00005 |
| ↳ 只看換場合 | **+0.0213** | +0.011 ～ +0.031 | 0.00010 |
| **只有三角色、拿掉硬條件** | **−0.1159** | −0.143 ～ −0.089 | 0.00005 |

**最後一列是重點，也是誠實的地方**：三個具名項**不能取代硬條件過濾**，只能加在它上面。
「這件但換成海軍藍」的「海軍藍」仍然必須是不可放寬的硬條件（§3.2），
角色項補的是硬條件之外的那半句——「其餘保持像那一件」與「不要再有黑色」。

**延遲**：批評請求 13.9 ms → **27.0 ms**（多兩次文字編碼），只在有批評的輪次發生，遠在 1.5 秒預算內。
**已設為服務 arm `full_zclip3` 預設**；對照 arm `full_zclip3_noroles` 保留舊行為。

### 3.35 使用者直接說「不要黑色」：當輪就生效，而且給得出替代（**已上線**）

**問題**：`retrieval_text` 裡的否定詞，CLIP 系編碼器接近隨機（NegBench, ICML 2025）。
先前我們**只發警告**（叫 ENGINE 01 去改成 `excluded_values`），所以如果 ENGINE 01 沒改，
系統會回 200、附上一份忠實的分數分解，然後**把使用者剛剛否決的東西端上來**。

**做法**：`engine02/negation.py` 把否定片語對到**商品庫自己的詞彙**，當輪加進
`constraints.excluded_values`（硬條件，永不放寬），並在 `constraint_report.honoured_negations`
寫明「你說的『不要黑色』我做了什麼」。它**刻意不猜**：

| 規則 | 擋掉的誤判 |
| --- | --- |
| 只對商品庫真的有的值觸發 | 亂排除不存在的東西；對不到就退回原本的警告 |
| 線索詞必須緊鄰（中文 10 字／英文 3 詞） | 「不要黑色」 vs 一整句話裡遠處的「不」 |
| 遇標點與連接詞就停 | 「不要黑色，**藍色可以**」→ 只排除黑色 |
| 同一個窗口內取修飾語、不取主詞 | "no black shirts" → 排除黑色，**不排除襯衫** |
| 只加排除，不動使用者要的東西 | 「我想要黑色襯衫」→ **不觸發** |
| 顏色以**色系**展開 | 「不要藍色」原本只排除 `Blue`，`Navy Blue` 照樣出現 |

設計要素的否定（「不要有明顯 logo」「不要太正式」）不是硬條件，走 `design_adjust_steps` 給
**−2 步**（明講的排斥比按一次倒讚更強），一樣寫進回應。

**實測**（`scripts/eval_negation.py`，`kagl_polyvore_filled`、marqo-fashionSigLIP、
把每句查詢自己前 5 名裡最常出現、**且不是它自己要求的**那個顏色寫成「不要 X」，29 句符合條件）：

| arm | violation@5（還在出現被拒色） | 空結果率 | NDCG@5 | 觸發率 |
| --- | --- | --- | --- | --- |
| `full_zclip3_noneg`（舊行為：只警告） | **0.214** | 0.000 | 0.6802 | 0% |
| `full_zclip3`（上線） | **0.000** | 0.000 | **0.7256** | 100% |

違反率 −0.214（CI −0.241～−0.186, **p=0.00005**）；NDCG@5 **+0.045（p=0.0007）**——
遵守使用者的排除**沒有代價，反而更準**，因為被拒色的商品本來就在跟真正相關的商品搶版面。
**要照講的限制**：120 句裡只有 29 句符合條件（其餘的前 5 名是它自己要求的顏色，
把那個排掉是自相矛盾不是否定），所以這是小樣本上的乾淨結果，不是大規模結論。

**「還要給得出替代」**：排除會拿走東西，所以回應同時回 `constraint_report.substitutes`——
被排除掉的那件裡分數最高的一件（限同品類），以及**螢幕上**離它最近的那一件，
並寫「你說不要黑色，這件是最接近被拿掉那一件的替代」。它是**報告不是排序決定**，
順序完全沒變；而且替代品是在多樣化決定最終名單**之後**才指定的，
所以它一定是使用者真的看得到的那五件之一（`tests/test_silent_failures.py` 釘住這件事）。

### 3.36 和 ENGINE 01／03 接起來：邊界只在一個檔案裡（**已完成**）

**問題的真面目**：ENGINE 01 的 prompt 是刻意用中文寫的，輸出**全部是繁體中文自由文字**
（`item_type: "連帽外套"`、`occasion: "約會"`、`fit: "修身"`），而且它的正確率測試是**逐字比對中文**，
所以那些值不會英文化。我們的商品庫是英文 KAGL 詞彙（`Shirts`、`Formal`、`Navy Blue`）。
**中文值直接送進來不會報錯**——它會通過放寬階梯，然後回一批很有自信、但完全不對的卡片。

**做法**：整個邊界收斂在 `engine02/intent_adapter.py`，並遵守三條規則：

| 規則 | 具體行為 |
| --- | --- |
| **不憑空造條件** | 對不到商品庫值的詞留在檢索文字裡並列入 `unresolved`，絕不變成硬過濾 |
| **`inferred_fields` 保持軟性** | ENGINE 01 標記「GPT 推論而非使用者說的」欄位 → `SlotState.INFERRED`，只進檢索、不砍候選池 |
| **用不了的要說出來** | 預算沒有對應欄位（`price` 欄 100% 是空的），直接回報而不是假裝有過濾 |

**測出來的四個坑（都已修）**：

1. 「秋冬」只解析成 Fall，Winter 整個消失——而這個字串就在 ENGINE 01 自己的測試集裡。
2. 「深藍色」被塌成色系代表值 `Blue`，把 195 件 `Navy Blue` 排除掉。現在特定色詞對到特定值，
   而**裸的色系詞（「藍色」）展開成該色系的所有值**。
3. **`style_keywords` 裡的否定被算成正號**：「不要太正式」原本加了 +2 的「正式感」，
   也就是**把排序往使用者說的反方向推，還附上一份有自信的解釋**。現在否定會翻號，
   而且被否定的詞**不會進檢索句**（CLIP 系對否定接近隨機）。
4. 使用者這句話裡說的偏好原本寫進 `feedback.design_adjust_steps`，卡片就變成
   「對應你想要的『你上一輪的回饋』」——**歸因錯誤**。現在走 `stated_design_steps`，
   卡片寫「你這句話裡說的」。

**回程（ENGINE 03）**：他們宣告的是 `attribute_scores` ＋ `free_text`，我們用的是「本輪展示／選擇／排除」的帳本。
`feedback_from_engine03()` 讓兩邊都不用改契約：分數滑桿 = **一步**（比使用者親口說的兩步弱），
而 `free_text` 走**和查詢端同一個否定解析器**，所以在回饋框打「不要黑色」會**真的被執行**（整個色系一起排除）。

**符合度分數（`match_score`）**：團隊 repo 只有散文定義、沒有公式、沒有實作。
我們照散文定義實作：**使用者說出口的要求（硬條件值＋指名的設計軸）在這批卡片上被滿足的比例**。
它**會下降**，而且刻意附上三個防作弊機制：
- 放寬過條件時一併回報 `relaxed`（否則 100% 是倖存者偏差）；
- 送 `prev_intent` 就同時回「用本輪意圖評」與「用上一輪意圖評」——
  **只有前者上升代表是意圖變寬鬆，不是結果變好**；
- 絕不拿排序分數當符合度（那是循環論證：ENGINE 03 調高權重，分數依定義必然變高）。

**框架**：服務層在 `backend/engine02_retrieval/`（`POST /retrieve`、`GET /health`，
並把 ENGINE 02 完整 API 掛在 `/engine02/*`）。套件本身留在根目錄，因為四個模組用
`parents[1]` 解析資料路徑，搬家會讓所有預設路徑、14 個測試檔與 40+ 腳本失效。
測試固定樣本直接取自 ENGINE 01 的 `test_cases.json`，共 15 項，GPU 與 CPU 都驗過。

### 3.37 趨勢預測：做，但附上回測（19 條真實序列，**已上線為面板**）

**為什麼先前說不做，現在做了**：先前拒絕的是「把趨勢分數放進排序」（§3.15，28 組設定全部變差）
與「宣稱能預測下一季銷量」（§3.20，公開 SOTA 誤差等於銷量本身）。
這兩件事現在依然不做。改變的是我們找到了**可以被回測的公開序列**，
所以「預測」可以從一句宣稱變成一個有對照、有誤差棒、可被否證的數字。

**資料**：Wikimedia Pageviews（免金鑰、資料 CC0、匿名 10 req/min），
`scripts/fetch_trend_history.py` 抓 19 個服飾條目 2019-01-01 至今的每日瀏覽數
（共 2,817–2,818 點／條，**0 條失敗**），彙整成週序列。
條目清單與每一列的污染風險（例如 `cardigan` 最大的同名對象是威爾斯地名）在
`docs/research/live-trend-sources.md`。**這量的是注意力，不是需求。**

**協定**：滾動原點回測（10 個視窗）、h = 8 週、m = 52 週、MASE 以樣本內季節性天真 MAE 標準化
（Hyndman & Koehler, IJF 2006），並對每條序列的分數做配對排列檢定（20,000 次）——
與 §3.1 檢索實驗**同一套證據標準**。

| 模型 | 平均 MASE | 中位數 | 贏過季節性天真 | 對基準的差 | p |
| --- | --- | --- | --- | --- | --- |
| 季節性天真（基準） | 0.879 | 0.828 | — | — | — |
| naive（重複上一週） | 0.693 | 0.650 | 15/19 | −0.185 | 0.0047 |
| drift | 0.702 | 0.672 | 15/19 | −0.177 | 0.0072 |
| SES | 0.651 | 0.632 | 15/19 | −0.228 | 0.0008 |
| Theta | 0.651 | 0.626 | 15/19 | −0.228 | 0.0007 |
| 季節性 Theta | 0.697 | **0.624** | 16/19 | −0.182 | 0.0008 |
| **組合（SES＋Theta＋季節性 Theta 平均）** | **0.583** | 0.518 | **18/19** | **−0.296**（CI −0.383～−0.207） | **0.0001** |

**這正是 M4 競賽的頭條結論在我們資料上重現**：簡單方法的**組合**贏過它的每個成分。
我們沒有用任何深度模型，也沒有需要——而這件事本身就是結果。

**誠實的部分**：

- **19 條裡有 1 條（`hoodie`，MASE 1.27）比基準差**，端點會把它標成 `trustworthy: false` 並附一句
  「這條序列上這個模型比重複去年同期差，不要用它下結論」。**會自己認輸的預測才值得相信。**
- 點估計做了**偏誤修正**：回測量到的每個展望期中位誤差被減掉，修正量原樣回傳在 `bias_correction`，
  未修正值留在 `point_uncorrected`。區間是去偏後誤差的分位數，**不是常態假設**。
- 序列只是**注意力**。`satin` 上升不代表九月的台灣市場正在從亞麻轉向緞面。
- **它不進排序**：`GET /trends/forecast` 自己回 `affects_score: false`。

**為什麼這件事在這個產業有價值**（`docs/research/backoffice-demand-prediction.md`）：
Heuritech 已經在賣製造商版的布料／版型兩年期預測（起價 12k€/年），EDITED 2026-03 也推出
Manufacturer Intelligence——**賣趨勢情報給製造商是紅海**。
但那份調查對七家廠商逐一查證的結果是：**同儕審查的準確率證據為 0**；
First Insight 自家 1,800 個 URL 的 sitemap 裡 accuracy/validation 命中 **0 個**。
整個服飾預測文獻（NFPPF survey 逐字確認）**沒有任何一篇報 MASE 或對季節性天真基準**。

所以我們的差異化不是「我們會預測」，而是：**我們的每一條預測都附一個可被否證的回測分數，
而這個產業沒有任何一家公開過。**

### 3.38 一次回饋要推多用力：量出來的劑量反應（60 位模擬購物者）

**評審當天會做的測試就是這一項**：給一則偏好回饋，看推薦有沒有跟著動。
`scripts/simulate_sessions.py` 讓 60 位模擬購物者走完 ENGINE 01 → 02 → 03 → 02，
每位抱怨一條設計軸，然後量**端出來的衣服在那條軸上的實際分數**（c(i,d) 的商品庫 z 單位）。

**先修好一個量錯的地方**：一開始我量的是卡片上的「貢獻」，但貢獻只在該軸有權重時才存在——
第一輪對「還沒被抱怨的軸」根本沒有那一項，60 場只剩 8 場可比，答案是 50%（丟銅板）。
改成量商品本身之後 n=60，才看得到真正的劑量反應：

| 一次抱怨算幾步 | 往正確方向動 | 平均位移 | **中位位移** | 前 5 名重疊 | 超出預算 |
| --- | --- | --- | --- | --- | --- |
| 1（原本） | 60.0% | −0.180 z | **−0.019 z** | 37.0% | 0 |
| **2（已上線）** | **70.0%** | −0.296 z | **−0.167 z** | 39.0% | 0 |
| 3 | 76.7% | −0.385 z | −0.232 z | 39.3% | 0 |

**中位數那一欄是重點**：一步的中位位移是 −0.019 z，也就是**中間那半數的使用者，畫面等於沒變**。
平均值 −0.180 看起來還行，是被少數大幅移動的場次拉起來的——只看平均會得到相反的結論。

**決定**：ENGINE 03 的契約每個 op 只能送 ±1，所以增益放在我們這側，
`ArmConfig.adjust_gain = 2`，與 §3.35 對「明講的排斥算兩步」一致。
ledger 會寫明「一次回饋算 2 步」，所以卡片上的數字解釋得通。
對照 arm `full_zclip3_gain1` 保留原本行為。

**沒有付出的代價**（同一批模擬）：前 5 名重疊率 37.0% → 39.0%（幾乎不變，代表不是靠亂換取得位移）、
超出預算的卡片 **0 張**、ENGINE 03 的 op 被拒絕 **0 個**、60/60 場全部成功。
**沒有選 3 的理由**：再往上推位移仍在增加，但那是把使用者原本說的話越推越遠；
2 是在「看得見的反應」與「仍然尊重使用者原句」之間，而且與既有的明講排斥同一個尺度。

## 4. 給其他引擎的需求

### 4.1 ENGINE 01
1. 硬條件的值要對到商品庫詞彙：品類是 `top/bottom/outerwear/dress/shoes/bag/accessory/jewelry/other` 或子類名稱（如 `Shirts`）；顏色是 KAGL `baseColour`（如 `Navy Blue`）；場合是 `Casual/Formal/Sports/Ethnic/...`；性別是 `Men/Women/Unisex/Boys/Girls`。詞彙對不上會直接造成 T1 那種崩盤。
2. 另外產生一句英文 `retrieval_text`，**不含否定詞**；否定一律放進 `excluded_values`。
3. `need_id` 使用 `engine02/resources/kansei_v0.json` 裡的 id（目前是草稿，M3 要用 GPT 填值、人工校正）。

### 4.2 ENGINE 03
1. `adjust` 只傳步數（±1），不要傳權重數字；換算在 ENGINE 02 做，這樣同一句回饋的結果可以重現。
2. choice 的 S(i|n) 請直接用回傳的 `design_scores`，不要自己重算 c(i,d)。
3. Rocchio 目前沒有顯著效果，**不要在簡報上宣稱它有效**；批評回饋（exclude／require）才是主要的進步來源。

## 4.3 串接方式
- **API**：`uvicorn engine02.api:app --port 8002`。環境變數 `ENGINE02_ENCODER` 可設 `marqo-fashionSigLIP`、`fashion-clip`，或 `hash`（不載模型，用於測試）。
- **端點**：

  - `POST /view`：排序＋PRD §7 的所有面板（你說的 vs 你沒說的、需求面板、Div@k、資料來源、兩輪 diff、趨勢標籤）。**前端不要自己從卡片重算這些聚合值**，它們是用產生排序的同一組 contribution 算的
  - `POST /complete-look`：搭配推薦（品類用 NPMI，商品用 OutfitTransformer 互補頭；分數是負距離，只在同一格內可比）
  - `POST /concept-image/nearest`：概念圖最近的 3 件（純展示，刻意不走 reranker）
  - `GET /needs/supply`：Sup(n)，ENGINE 03 算缺口乘積要用的供給側
  - `GET /trends`：趨勢標籤關鍵字（`ENGINE02_TRENDS=1` 才載入），`used_in_ranking` 永遠是 false
  - `GET /vocabulary`：ENGINE 01 正規化要用的商品庫詞彙
  - `GET /kansei`：need 與 design element 的 id
  - `GET /items/{id}`、`GET /images/{id}`：商品資料與圖片
  - `GET /arms`、`GET /health`（含載到哪些 OutfitTransformer 頭）
- **規格檔**：`docs/contract/`，含 request／response 的 JSON Schema，以及第 1、2 輪的範例 request／response；範例是 ENGINE 03 把「太像上班族，不要黑色＋點選第 3 件」轉成回饋之後的真實輸出。
- **回傳的輸入警告**：`constraint_report.input_warnings` 會回報 ENGINE 01 該修的問題——`retrieval_text` 殘留否定詞（中英都抓；CLIP 系對否定接近隨機，NegBench ICML 2025，否定請放 `excluded_values`）、以及 `retrieval_text_normalized=false` 導致本輪只走 dense。
- **三個規則指標**：`metrics.feedback_violations` 現在剛好等於 `excluded_value_hits + rejected_item_hits`（口徑：**累計所有先前輪次**的回饋，不只第 1→2 輪；兩者在第 2 輪相同，累計版只會多報不會漏報）。
- **理由方向**：權重為負的設計要素一律寫成「避開〇〇」。例如「避開正式感（+0.93），對應你想要的『你上一輪的回饋、怕顯得太用力』」，避免被讀成「因為很正式才推薦」。

## 4.4 GPU 實測（nycu，RTX 4090）
- **Qwen3-VL-Reranker-2B**（bf16）：每個 pair 9.6 ms，4.25 GB VRAM。48 張圖的 MRR 0.74（隨機 0.09）。top-50 重排約 0.5 秒，**可以在 demo 現場開**。
- **Qwen3-VL-Reranker-8B**：sentence-transformers 路徑載入失敗（`LogitScore` 缺 `true_token_id`），已排程改用官方 repo 的類別重測。
- **Qwen3-1.7B**：bf16、3.4 GB VRAM，這次改寫正確保留了「長袖可能稍熱」的注意事項，但仍然要做事實檢查。
- **Qwen3-VL-8B 屬性標註**：每件約 0.1–0.18 秒，5,000 件約 15 分鐘。
- **商品庫一致性**：伺服器上重建的 KAGL 5,000 件與本地完全相同（5000/5000 ID 一致），結果可以直接比對。
